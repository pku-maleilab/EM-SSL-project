Importing Your Own Models

Napari-OmniEM ships with built-in tasks, but you can add your own fine-tuned OmniEM models to any task through Preferences → Tasks and Models → Add Solution.

Every model is stored as a small task head on top of a shared backbone (see Backbones below). When you import a model you tell the plugin which backbone it belongs to and which head to use; the plugin copies the head into its managed weights folder and records it.

Before you start

  • A model-config file (.yaml) that describes the model (architecture, task type, number of output labels, normalization statistics). Use the config that was shipped alongside the weights: see the warning below.
  • A weights file (.pt), either a full checkpoint (backbone + head in one file) or a head-only file that was split from one.

Match the config to the weights

A model-config .yaml is not cryptographically tied to a checkpoint; nothing stops you pairing the wrong two. Always use the config file that was distributed with those weights. A mismatched config passes the file checks but produces wrong results or fails when the model loads.

Add a solution

  1. Open Preferences (⚙️) → Tasks and Models → Solutions, select the task the model belongs to, and click Add Solution.
  2. Select the model config (.yaml). Its contents appear read-only so you can confirm the architecture, task type, label count, and normalization.
  3. Choose an import strategy:
    • Full-scale (.pt): a complete checkpoint. On import the plugin splits it into the shared backbone plus a task head. If a matching backbone is already registered, only the new head is kept and the existing backbone is reused; if the backbone is new, you are offered a chance to name it.
    • Head-only (split .pt): a head file produced by a previous split. This option is available only when a matching backbone is already registered (the head needs a donor backbone to run).
  4. Pick the weights file, then confirm. The head is copied into the managed weights folder as head_<task>-<solution>.pt.

If the import is rejected

The plugin validates the model before writing anything, so a rejected import leaves no files behind. Common messages and what they mean:

Message Meaning
Unsupported model / encoder The config's architecture is not one this build supports.
Task type mismatch The config's task type doesn't match the task you're adding to (Image-to-Image vs Image-to-Label).
Label count mismatch An Image-to-Label config declares a different number of labels than the task.
Backbone / encoder mismatch The head was trained for a different backbone than the one selected.

Sharing and exporting

Once a solution works you can package it for someone else, or repackage its weights:

  • Export Weights (Solutions tab) writes this solution's weights out as either a Combined single .pt or a Split pair (backbone + head). Combined files load anywhere; split pairs are smaller to share when the recipient already has the backbone.
  • Dump Task / Import Task move a whole task (all its solutions) between installs. See Task & Solution Management for the full sharing workflow. Note that Dump writes the task description only; the weights are exported separately and must sit in the folder you point Import at.
  • The File Management tool (🧰 → File Management) can split a combined checkpoint or merge a backbone + head back into one file without adding a solution. See Tools Workbench.

Backbones

Every model runs on a shared backbone: one large ViT-L encoder (EM-DINO, shown as EMDINOv1-ViTL). The backbone is loaded once and borrowed by every task that uses it, so keeping several models ready does not reload the encoder and keeps GPU memory low. Backbones are managed under Preferences (⚙️) → Tasks and Models → Backbones.

The backbone inventory

The Backbones table lists one row per registered backbone:

Column Meaning
Display Name Friendly name (defaults to the tag).
Tag Short content fingerprint that identifies the weights.
Arch Encoder architecture (e.g. emdinov1).
Solutions How many task heads currently reference this backbone.
Actions Rename and Remove for this backbone.

The built-in backbone (4246a479, EMDINOv1-ViTL) is always present and its Remove action is disabled.

Add a backbone

Click + Add Backbone. There are two ways to add one:

  • Register split .pt: point at a standalone backbone file (already split out of a checkpoint). It is copied into the managed weights folder and registered.
  • Extract from combined .pt: point at a full checkpoint; the backbone part is extracted, stored, and registered, leaving the original file untouched.

Rename changes only the display name (up to 64 characters); the tag never changes.

Remove a backbone

Selecting Remove does different things depending on the backbone, and it never silently deletes something another model needs:

  • Built-in backbone: cannot be removed.
  • In use: if any model is currently loaded on it, or any solution references it, removal is blocked. Unload the models (🧰 → Memory Management → Remove) or remove/reassign the solutions first.
  • External file (stored outside the managed weights folder): removed from the registry only; the physical file is left where it is.
  • Managed file (inside the weights folder, unreferenced): you are asked whether to also delete the file or just deregister it.

Two different “remove”s

Preferences → Backbones → Remove takes a backbone out of the registry (and optionally deletes its file). 🧰 → Memory Management → Remove backbone only frees it from memory for this session; it stays registered. See Tools Workbench.

Backbone settings

The weights storage folder and the backbone cache size are set in Preferences → Settings → General settings; see the Preferences reference.

  • Weights storage folder: where the plugin keeps backbone_<tag>.pt and head_*.pt. Changing it offers to move the existing managed files to the new location.
  • Backbone cache size: how many distinct backbones may stay resident at once. Sharing one backbone across tasks is what keeps multi-task GPU use low.
